### 已选定的扩展方向

正确性统一在实数语义下证明。两道数值门负责决定原子关系能否成为浮点等价理论的假设：

- Bias gate 比较候选与参考输出的带符号分桶差异。
- Vars gate 比较两者相对高精度 oracle 的峰值误差放大及其尾部。
- 双 PASS 接受；FAIL 拒绝；WARN 保留为带警告结果，由契约决定是否允许替换。证据不足单独记录，不归为 PASS。

原子数值检查依赖 dtype、累加精度、shape、输入分布、权重、阈值和证据，并且具有方向性。被准入的原子关系作为显式假设参与形式等价推导，允许对称、传递和共同语句上下文；这些证明规则不宣称统计检查可以反向或组合，也不构造具体 IEEE 位值的 Lean 等式。完整定义、结合律例子、接入边界和待验证保证见 [TwoGatesAcceptance.md](./TwoGatesAcceptance.md)。

以下各节保留对**当前实现**的核对，作为扩展工作的基线。

### 函数参数与已有约束

当前抽象的是舍入行为，不是把浮点数本身或所有浮点运算都变成未解释函数。[RoundingModel.lean](../VeriTile/Triton/Float/RoundingModel.lean) 的实际定义为：

```lean
structure RoundingModel where
  round : FloatDType → ℝ → ℝ
  round_real : round .real = id
  round_idem : ∀ dtype x, round dtype (round dtype x) = round dtype x
```

更准确的术语是 **abstract rounding function** 或 **rounding-model-parametric semantics**。如果用 uninterpreted function 来帮助理解，应说明它是带显式约束的黑盒舍入函数；在 Lean 中，它是结构体的函数参数，并不固定为某个 IEEE 实现。

记 `q_d(x) = R.round d x`。每个模型默认要求 `q_real(x) = x`，以及同一 dtype 的幂等性 `q_d(q_d(x)) = q_d(x)`。单调性 `MonoRounding`、奇对称性 `OddRounding`、较窄格式到 fp32 的可表示值包含关系 `GridNested` 都是按定理选择的额外假设。模型没有默认要求舍入保持加法、乘法或结合律，也没有定义具体误差界、尾数位数或 IEEE 特殊值行为。

不同 dtype 使用不同的函数参数位置，但定义并不要求这些函数两两不相等。`RoundingModel.triv` 将所有舍入函数取为恒等函数；已有退化定理把该实例的执行连接到原来的精确语义。一个对任意 `R` 成立的定理，其结论也可能显式依赖 `R`，不代表输出对所有舍入模型都是同一个数。

### 结合律在哪一层成立

[Scalar.lean](../VeriTile/Triton/Semantics/Scalar.lean) 中，`.fp32`、`.fp16`、`.bf16` 等标签的普通加法和乘法仍使用提升到 `WithBot ℝ` 的实数运算。[EvalOpR.lean](../VeriTile/Triton/Float/EvalOpR.lean) 的普通 `add`、`mul`、`reduceSum`、`dot` 分支不自动在每一步插入舍入；显式 `castFloat` 才调用 `R.cast`。浮点 store 通过 [StepR.lean](../VeriTile/Triton/Float/StepR.lean) 调用对应 dtype 的舍入函数。

因此，对有限实数值，**没有中间舍入的算术段可以使用实数结合律**。这来自运算的定义和实数定理，不是额外假设了一个“IEEE 浮点加法结合律”。仅将表达式标成 `.fp32`，不会让普通加法自动获得逐操作 fp32 舍入。

| 表达式关系 | 当前模型能否默认成立 | 原因 |
|---|---|---|
| `(a + b) + c = a + (b + c)` | 能，针对无中间舍入的实数算术 | 实数结合律 |
| `q_d((a + b) + c) = q_d(a + (b + c))` | 能 | 先证明实数参数相等，再应用同一个函数 |
| `q_d(q_d(x)) = q_d(x)` | 能 | 模型字段 `round_idem` |
| `q_d(q_d(a + b) + c) = q_d(a + q_d(b + c))` | 不能作为通用等式使用 | 中间舍入位置不同；实数结合律和幂等性不足以推出 |
| `q_d(a + b) = q_d(a) + q_d(b)` | 不能作为通用等式使用 | 没有加法同态假设 |
| `q_d(q_e(x)) = q_d(x)`，其中 `d ≠ e` | 不能仅凭幂等性推出 | `round_idem` 只覆盖同一 dtype |

这里的 `a`、`b`、`c` 是实数值，`q_d` 是固定 dtype 的舍入函数。若要建模每次加法后都舍入，应明确表示 `q_d(a + b)` 这样的操作；当前 evaluator 不会自动做这件事。真实浮点算术一般不满足结合律，不能把上表前两项解释成硬件重排的逐位等价保证。背景参考：[Goldberg 的浮点算术说明](https://docs.oracle.com/cd/E19957-01/806-3568/ncg_goldberg.html)。

### 当前抽象舍入能力的表述

> 将舍入点保留为按 dtype 区分、受显式性质约束的函数应用，并在同一模型下证明 kernel 变换的正确性与等价性，使结论可适用于一类满足这些性质的舍入函数，而不依赖某个具体舍入实现。

这一表述的范围是当前建模的 cast/store 舍入事件。它仍以事件之间的精确算术为基础，不涵盖自动建模每步硬件浮点误差的承诺。抽象函数这一手段本身是否足以构成新颖性，需要结合语义设计、可证明的变换和实际复用收益来判断。

现有 [SwiGLU 案例](../bench/examples/FusedSwigluEquiv.lean) 是较直接的正例：fused 版本显式保留中间 bf16 cast，unfused 版本的同 dtype 重复舍入可用幂等性消去，因此两者在同一个 `R` 下输出相等。该结论不是允许任意删除中间量化，也不是依靠默认接受舍入后的结合律；其独立 launch 边界仍见下文。

## 核心案例的具体缺口

### SwiGLU fusion

当前 [FusedSwigluEquiv.lean](../bench/examples/FusedSwigluEquiv.lean) 的 headline 对比的是 fused kernel 与 `ComputeKernel.seq` 拼接的两个 body。拼接执行允许寄存器跨阶段保留，文件明确说明该结论针对 concatenated kernel。

如果论文要展示两次独立 launch 到一次 fused launch 的重写，需要为该案例建立连接到 `execPipelineR` 的结论。[Pipeline.lean](../VeriTile/Triton/Float/Pipeline.lean) 已有 `ComputeKernel.execR_seq_rel_execPipelineR`，后续应检查并补齐成功投影、register-closedness 等前提。该连接仍然是模型内部的定理，不升级为 CUDA runtime 认证。

### Online softmax

当前 [OnlineSoftmaxCorrect.lean](../bench/examples/OnlineSoftmaxCorrect.lean) 的最终 `online_softmax_correctness` 声明针对 `batchSoftmaxIO`：batch kernel 实现由 online recurrence 定义的数学函数。文件中的 streaming kernel 证明主要描述寄存器递推结果，kernel body 没有最终输出 store。

如果把它作为完整 streaming kernel 验证案例，需要补输出阶段并连接到对应 IO 定理；也可以保留当前结果并准确限定论文主张。文件名和递推恒等式本身不能替代完整 streaming 输出定理。

### LayerNorm 与 attention

[FusedLayerNormEquiv.lean](../bench/examples/FusedLayerNormEquiv.lean) 已有 two-pass 与 Welford 版本的等价性案例，值得直接复用。其归约和 affine 算术运行在实数模型中，舍入位于输出 cast/store；不能据此声称硬件中间浮点运算逐位等价。

Attention 案例应在 M2 中按完整计算范围、参数化程度和证明成本选择。现有 FlashAttention 相关证明包含不同布局、阶段和边界条件，不能将其中一个切片的结果概括为所有生产路径均已验证。

| 参数泛化与复用 | 一个证明覆盖哪些配置，修改后需补多少证明？ | 复用参数化案例；从新变体开始记录过程与成本 |
| 方法比较与消融 | 组合接口和共享引理带来了什么收益与代价？ | 固定共同任务、性质和预算，分别报告支持范围、成本和未完成情况 |
| Two-gates 接受关系 | 两门如何区分可接受变换和数值缺陷，代价与统计限制是什么？ | 新增具体浮点执行、正负对照、单门/双门消融及不同 dtype/输入分布评估；报告数据待复现 |

比较对象优先研究 [VOLTA](https://arxiv.org/html/2511.12638v1)。其论文对静态已知尺寸和特定结构的 GPU kernels 做等价性检查。一个待检验的差异化假设是：参数化证明能否减少跨尺寸、跨变体的重复工作，以及建立这种证明的成本是多少。该方向尚未通过比较实验，不能预先写成性能或能力优势。

实验协议应遵守以下区分：

- 已有证明检查成功率不等于新任务的自动证明成功率。
- 参数化定理的量化范围来自定理，不来自有限 shape 测试。
- 证明未完成、超时、不支持、基础设施失败和证实错误分别记录；旧 proof 在 mutation 后无法通过，不足以单独判定 kernel 错误。
- 历史人工投入没有可靠记录时，不事后补造精确数据；新变体使用前瞻记录。
- 不同方法比较时说明数值模型、输入域、特化条件、源语言及信任边界的差异。

### 按论文主张选择的补充实验

**所选 two-gates 路线需要实际 GPU 实验。** Lean 检查、验证耗时、内存使用、证明复用和人工成本仍可在 CPU 上评估；数值原语明确由 Python 调 Triton/GPU，运行测试不替代实数正确性证明或硬件语义认证。

当前开发环境没有 NVIDIA GPU。按用户安排，将运行配置、14 条 Triton 原子关系、checker 和结果导入推送到独立 dev 分支，由用户在 GPU 机器运行并回传完整结果目录。CPU 统计回归、解释器索引测试和离线编译不登记成 GPU 通过结果。

**LLM 实验也不是默认主线。** [bench/README.md](../bench/README.md) 已记录旧 LLM proof-drafting benchmark 的退役，现有 `scripts/prove.py` 是单任务 agent-assisted proof wrapper。如果后续选择声称自动证明能力，需要另外建立固定任务、固定预算、独立判定、成功率与失败分析的实验；当前论文可以如实定位为人工辅助验证框架。
